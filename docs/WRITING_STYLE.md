# 한국어 문서와 주석 작성 기준

README, 설명서, 코드 주석, 화면 문구를 고칠 때 적용합니다. 독자가 해야 할 일과 코드가 실제로 하는 일을 쉬운 한국어로 씁니다. 비전공자용 설명에 필요한 예시와 절차는 충분히 남깁니다.

## 먼저 보존할 내용

- 명령어, 코드 블록, 경로, API 이름, 모델명, 수치, 날짜, 단위, 인용과 출처를 유지합니다.
- 필수 조건과 선택 사항을 구분합니다. 가능성·제약·미검증 상태를 문체 교정 중에 확정 사실로 바꾸지 않습니다.
- 문서의 독자와 말투를 유지합니다. 설명서를 광고문이나 수필로 바꾸지 않습니다.
- 실제로 하지 않은 경험, 개인 감상, 확인하지 않은 사례를 추가하지 않습니다.

## 문장 검토

누가 무엇을 하는지 보이는 문장을 우선합니다. 추상적인 명사를 길게 나열하거나 같은 동사를 반복한다면 실제 동작으로 풀어 씁니다. 원인과 결과가 필요한 문장에는 연결 관계도 남깁니다.

아래 표현은 문맥을 읽고 고칠 후보입니다. 단어가 있다는 이유만으로 일괄 삭제하지 않습니다.

| 살펴볼 구간 | 고치는 방법 |
|---|---|
| 번역투와 이중 피동 | 행위자를 드러내거나 자연스러운 동사로 씁니다. |
| 의미 없는 도입·결산·의의 강조 | 독자에게 필요한 내용부터 씁니다. |
| 반복되는 부정 대비 | 실제 차이를 이해하는 데 필요한 대비만 남깁니다. |
| 비슷한 길이·종결이 계속되는 문장 | 연결된 설명은 문단으로 묶고 중요한 구분은 분리합니다. |
| 연결어미 바로 뒤에 붙는 습관적인 쉼표 | 문맥상 필요할 때만 쓰며 윤문 과정에서 불필요한 쉼표를 늘리지 않습니다. 인용과 코드의 쉼표는 보존합니다. |
| 같은 경고·범위 설명의 반복 | 필요한 위치에서 정확히 설명하고 다른 곳에서는 해당 절로 연결합니다. |
| 과한 굵게 표시·대시·괄호·따옴표 | 읽는 데 도움이 되는 표시만 남깁니다. |
| 목적 없이 늘어나는 표·목록 | 비교·순서·대응 관계가 있으면 유지하고 나머지는 문장으로 씁니다. |

짧은 문장이나 `할 수 있습니다`, `아닙니다` 같은 표현도 필요할 때 씁니다. 기계적인 횟수 제한에 맞추려고 사실이나 조건을 바꾸지 않습니다. API 표, 설치 순서, 주의 사항처럼 기술 문서에 필요한 형식도 유지합니다.

## 검수 순서

1. 독자와 문서의 목적을 확인합니다.
2. 어색한 구간과 이유를 짚고 그 부분만 고칩니다.
3. 원문과 비교해 명령·수치·기술적 의미·조건이 유지됐는지 확인합니다.
4. 설명의 흐름과 반복을 다시 읽고 링크를 확인합니다.
5. 바꾼 예와 남겨 둔 한계를 기록합니다. 문체만으로 작성 주체를 단정하거나 AI 판별 확률·점수를 만들어 보고하지 않습니다.

작업을 나누는 에이전트는 담당자에게 이 문서 경로와 보존할 내용을 함께 전달합니다. 최종 검토자는 각 수정본과 원문을 대조합니다.
