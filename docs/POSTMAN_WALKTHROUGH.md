# Postman으로 기록 만들기를 처음부터 따라가기

[README](../README.md)에서 브라우저로 사진을 올리고 질문에 답한 과정을 이번에는 Postman으로 반복합니다. 버튼 대신 요청을 한 개씩 보내면서 서버가 돌려준 값을 다음 요청에 넘겨 보겠습니다. 여기까지 마치면 기록 ID, 현재 질문 ID, 버전이 각각 왜 필요한지 구분할 수 있습니다.

먼저 로컬 앱을 실행해 둡니다. 앱을 켠 PowerShell은 그대로 두고 Postman을 여세요. 처음에는 외부 AI를 호출하지 않는 `demo` 모드로 진행합니다. NCP 주소에서 `ncloud` 모드로 실행하면 실제 사진 저장과 AI 사용에 따른 비용이 발생할 수 있습니다.

이 실습에서는 `2026-10-29`에 동네 카페에서 발표를 마친 뒤 쉬었다는 가상 기억을 만듭니다. 사진은 저장소의 `scripts/fixtures/test-photo.png`를 사용해도 됩니다. 브라우저에서 만든 기록을 가져오는 대신 Postman에서 새 테스트 기록 하나를 만들어 끝까지 따라갑니다.

## 1. 요청 모음을 가져오고 주소를 맞추기

Postman의 **Import**에서 저장소의 `postman/photo-memory-app.postman_collection.json`을 선택합니다. 가져온 컬렉션 이름은 `사진 너머 — 완성 앱 API 실습`입니다. 안에는 `01`부터 `10`까지 번호를 붙인 요청이 들어 있습니다.

컬렉션의 변수 설정에서 `base_url`을 확인합니다. 로컬 앱이면 `http://127.0.0.1:3000`을 그대로 쓰고 NCP에서 실행 중인 앱이면 본인의 실제 서비스 주소로 바꿉니다. 주소 뒤에 `/api/app`까지 넣지 않습니다. 각 요청이 필요한 경로를 뒤에 붙입니다.

요청 주소의 `{{base_url}}`은 이 변수의 값을 넣으라는 표시입니다. `{{memory_id}}`와 `{{question_id}}`도 같은 방식으로 바뀝니다. 처음에는 직접 ID를 만들거나 다른 프로그램에서 복사하지 않아도 됩니다. 성공 응답을 읽는 스크립트가 다음 값을 보관합니다.

| 컬렉션 변수 | 성공 응답에서 가져오는 값 | 다음에 쓰는 곳 |
|---|---|---|
| `memory_id` | `data.memory.id` | 이후 모든 기록 주소 |
| `memory_version` | `data.memory.version` | 제목·본문 저장, 초안 재작성 |
| `question_id` | `turns` 중 `answer === null`인 질문의 `id` | 현재 질문에 답하기 |
| `record_title` | 비어 있지 않은 `data.memory.title` | 최종 저장의 제목 |
| `record_content` | 비어 있지 않은 `data.memory.content` | 최종 저장의 본문 |

이 처리는 응답에 `data.memory`가 있을 때만 실행됩니다. 목록 응답이나 삭제 응답으로 변수를 다시 고르지는 않습니다. 아직 답하지 않은 질문이 없을 때도 기존 `question_id`를 비우지는 않으므로 마지막 답변 뒤에는 변수가 남아 있다는 이유로 답변을 다시 보내지 마세요.

이제 `01 · 앱 모드 확인 + 익명 세션 발급` 요청을 열고 **Send**를 누릅니다. 방식은 `GET`, 주소는 `{{base_url}}/api/app`이고 Body에는 아무것도 넣지 않습니다. 응답 아래에서 HTTP 상태가 `200`인지, 본문의 `ok`가 `true`인지, `data.mode`가 `demo`인지 확인합니다.

서버는 필요한 경우 `memory_session` 쿠키를 발급하고 Postman은 같은 주소의 후속 요청에 이 쿠키를 보냅니다. 브라우저와 Postman은 쿠키를 자동으로 공유하지 않습니다. 브라우저에서 만든 기록 ID만 Postman에 넣으면 다른 사용자의 기록으로 판단해 `404`가 나올 수 있는 이유입니다. 실습 중에는 `127.0.0.1`을 `localhost`로 바꾸는 식으로 호스트를 오가지 않고 처음 정한 주소를 유지합니다.

`configured:true`는 필수 설정값이 있다는 뜻입니다. NCP의 DB·스토리지·AI에 실제로 연결됐다는 결과는 아니므로 여기서는 실행 모드와 서버 응답까지 확인한 셈입니다.

## 2. 빈 기록 하나 만들기

`02 · 기억 만들기` 요청을 엽니다. 방식은 `POST`, 주소는 `{{base_url}}/api/memories`입니다. **Body → raw → JSON**에서 기존 예시를 다음 내용으로 바꾼 뒤 **Send**를 누릅니다.

```json
{
  "date": "2026-10-29",
  "place": "동네 카페",
  "questionLimit": 3
}
```

`date`는 실제로 존재하는 날짜여야 합니다. `2026-02-30`은 날짜 형식처럼 보여도 거절합니다. 장소를 모르면 `place`를 `""`로 보내되 필드는 남깁니다. `questionLimit`은 숫자 `3`이며 따옴표로 둘러싼 `"3"`과 다릅니다. 선택 범위는 1~10이고 생략하면 기본값 3을 사용합니다.

응답의 `data.memory`를 펼쳐 `status`가 `upload`인지 확인합니다. 아직 사진이나 일기가 없는 준비 단계입니다. 이때 `id`가 새로 발급되고 `version`은 `1`입니다. 응답 후 스크립트가 둘을 `memory_id`와 `memory_version`에 넣으므로 다음 요청의 주소가 이 기록을 가리키게 됩니다.

## 3. 방금 만든 기록에 사진 넣기

`03 · 사진 1~3장 업로드`를 엽니다. 주소가 `{{base_url}}/api/memories/{{memory_id}}/photos`인지 확인한 뒤 **Body → form-data**를 봅니다. `files` 행의 종류를 **File**로 두고 파일 선택 버튼에서 테스트 이미지를 고릅니다.

두세 장을 넣으려면 이름이 같은 `files` 행을 추가하고 각 행에서 다른 파일을 선택합니다. 파일은 JPEG·PNG·WebP이며 하나에 5MiB 이하, 0바이트보다 커야 합니다. 브라우저에서 올릴 때와 달리 Postman은 사진을 자동으로 축소하지 않으므로 원본 크기를 확인해야 합니다. 기록 하나의 합계는 최대 3장이고 대화를 시작한 뒤에는 추가할 수 없습니다.

`Content-Type`은 직접 쓰지 않습니다. 파일을 나누는 경계 정보까지 포함해 Postman이 만들어야 서버가 사진을 읽을 수 있습니다. **Send** 후 `data.memory.photos`에 고른 사진이 들어 있는지 확인합니다. 사진 저장으로 `version`도 바뀌며 스크립트가 그 값을 보관합니다.

사진 자체를 조회해 보고 싶다면 별도 GET 요청에서 `{{base_url}}` 뒤에 응답의 `photos` 항목에 있는 `url`을 붙입니다. 이 요청은 일기 JSON 대신 이미지 바이트를 돌려줍니다. 같은 Postman 쿠키로 요청해야 사진 소유권 검사도 통과합니다.

## 4. 사진으로 첫 질문 시작하기

`04 · 사진에서 첫 질문 만들기`를 엽니다. 방식은 `POST`, 주소는 `{{base_url}}/api/memories/{{memory_id}}/start`입니다. 가져온 요청의 **Body → raw → JSON**에는 다음 객체가 들어 있습니다.

```json
{}
```

이렇게 보내면 기록 생성 때 정한 질문 수를 사용합니다. 시작 직전에 질문 수를 확정하려면 다음처럼 명시할 수도 있습니다.

```json
{ "questionLimit": 3 }
```

본문을 아예 지우는 대신 JSON 객체를 보냅니다. 사진이 최소 한 장 있어야 시작할 수 있습니다. **Send** 후 `status`가 `conversation`으로 바뀌고 `turns`에 첫 질문이 생겼는지 봅니다. `demo`에서는 준비된 질문을 사용하며 `ncloud`에서는 사진 관찰과 질문 생성에 외부 서비스를 사용합니다.

`turns`에서 `answer`가 `null`인 항목을 찾으세요. 이 질문의 `id`가 다음 답변에 필요한 질문 ID입니다. 기록 전체의 `id`와는 다릅니다. 스크립트가 현재 질문 ID를 `question_id`에 넣어 줍니다.

## 5. 현재 질문을 읽고 답변 보내기

`05 · 현재 질문에 답변 (선택한 질문 수만큼 반복)`을 엽니다. 방식은 `POST`, 주소는 `{{base_url}}/api/memories/{{memory_id}}/answers`입니다. **Body → raw → JSON**에 아래처럼 입력합니다. 예시 문장을 보내기 전에 실제 응답에 나온 질문과 이어지는지 읽어 보세요.

```json
{
  "questionId": "{{question_id}}",
  "answer": "발표가 끝나서 친구와 쉬고 있었어요.",
  "skipped": false
}
```

`questionId`는 서버가 준 현재 질문의 실제 UUID로 바뀝니다. `skipped`는 따옴표 없는 참거짓 값이며 `"false"`라는 글자를 보내면 거절합니다. 일반 답변은 공백만 넣을 수 없고 2,000자 이하여야 합니다.

**Send** 후 방금 질문의 `answer`에 보낸 문장이 들어갔는지 확인합니다. 질문이 남았다면 `turns` 끝에 새 질문이 생깁니다. 그 질문을 읽고 `answer`만 다음 답변으로 바꿔 다시 보냅니다. 새 질문 ID는 직전 응답의 스크립트가 갱신합니다.

이 가상 기억에서는 질문에 맞춰 “준비하면서 힘들었던 부분을 이야기했어요”, “끝내고 나니 마음이 놓였어요”처럼 이어 갈 수 있습니다. 질문이 실제로 무엇을 묻는지 확인하면서 자신의 테스트 답변을 넣으세요. 선택한 세 질문에 모두 답하면 답변이 `null`인 질문이 더는 생기지 않습니다. 그때는 초안 요청으로 넘어갑니다.

건너뛰기는 같은 요청에서 `skipped`를 `true`로 보내면 됩니다. 다만 실제 답변이 하나도 없게 되는 마지막 건너뛰기는 `400 ANSWER_REQUIRED`로 거절합니다. 초안의 근거가 될 답변이 최소 하나 필요하기 때문입니다. 충분히 답했다면 세 문항을 다 채우기 전에도 다음 단계에서 초안을 만들 수 있습니다.

같은 질문에 같은 답변을 다시 보내면 서버는 중복 저장하지 않고 현재 기록을 반환합니다. 이미 답한 질문에 다른 답변을 보내면 `409 ALREADY_ANSWERED`가 됩니다. 오류를 피하려고 임의의 질문 ID를 만들지 말고 최신 기록에서 현재 질문을 확인합니다.

## 6. 답변으로 초안 만들기

`06 · 내 답변으로 초안 만들기`를 엽니다. 방식은 `POST`, 주소는 `{{base_url}}/api/memories/{{memory_id}}/draft`입니다. **Body → raw → JSON**에 `{}`가 있는지 확인하고 **Send**를 누릅니다.

성공 응답의 `status`는 `draft`입니다. `title`과 `content`를 읽고 `turns`에 남아 있는 원래 답변과 비교합니다. `demo`에서 이 단계는 실제 CLOVA 글쓰기 품질을 확인하는 실습이 아닙니다. 요청 순서와 데이터 전달을 익히는 과정입니다.

응답 후 스크립트는 초안 제목과 본문을 `record_title`, `record_content`에 넣고 최신 `version`도 보관합니다. 이미 초안이나 저장된 기록이 있는 상태에서 같은 `{}` 요청을 다시 보내면 기존 기록을 반환하며 새 글을 생성하지 않습니다. 저장 전에 글을 다시 생성하는 선택 실습은 뒤의 [초안 재작성](#9-선택-실습-저장-전-초안-다시-만들기)을 참고합니다.

## 7. 제목과 본문을 확인하고 저장하기

`07 · 제목/글 확인 후 저장`을 엽니다. 방식은 `PATCH`, 주소는 `{{base_url}}/api/memories/{{memory_id}}`입니다. 가져온 요청의 Body에는 `{{save_payload}}`가 보입니다. 요청 직전 스크립트가 앞서 보관한 제목·본문·최신 버전으로 이 값을 JSON 문자열로 만듭니다. 줄바꿈이나 따옴표가 있는 본문도 `JSON.stringify`로 처리합니다.

초안을 그대로 저장하려면 내용을 읽고 **Send**를 누릅니다. 직접 수정하려면 컬렉션 변수의 현재 `record_title`, `record_content`를 고친 뒤 이 요청을 보냅니다. Body를 **raw → JSON**의 완전한 JSON으로 바꿔 보내는 방법도 있습니다.

```json
{
  "title": "발표 뒤의 휴식",
  "content": "발표를 마친 뒤 친구와 쉬었다. 준비하면서 힘들었던 부분을 이야기했다.",
  "version": 6
}
```

위의 `6`은 형식 예시입니다. 직접 JSON을 쓴다면 반드시 직전 응답의 실제 `data.memory.version`으로 바꿉니다. 번호를 먼저 올려서 보내지 않습니다. 서버는 그 버전이 아직 최신일 때만 저장하고 성공 후 번호를 올립니다. 버전이 다른 `409 VERSION_CONFLICT`가 나오면 상세를 다시 조회해 바뀐 내용과 자신의 편집 내용을 비교합니다.

저장 성공 후 `status`가 `saved`인지, 제목·본문이 보내려던 내용과 같은지 확인합니다. 제목은 80자, 본문은 32,000자 이하이고 빈 값이나 공백만 있는 값은 저장할 수 없습니다.

## 8. 다시 읽고 자신이 만든 테스트 기록 정리하기

`08 · 내 기록 목록`을 보내면 `GET {{base_url}}/api/memories`의 응답에서 `data.memories` 배열을 볼 수 있습니다. 방금 저장한 제목이 있는지 찾습니다. 이어서 `09 · 기록 상세 / 최신 version 읽기`를 보내면 `GET {{base_url}}/api/memories/{{memory_id}}`로 같은 기록을 다시 읽습니다.

상세의 제목·본문·질문·답변을 비교해 저장 내용이 유지됐는지 확인합니다. 상세 요청의 응답 후 스크립트도 `memory_id`, 최신 `memory_version`과 비어 있지 않은 제목·본문을 다시 보관합니다. 목록만 보고 저장을 추측하는 대신 실제 상세까지 읽은 셈입니다.

실습을 마쳤으면 상세에서 **방금 자신이 만든 테스트 기록**이 맞는지 확인한 뒤 `10 · 테스트 기록과 사진 삭제 (주의)`를 보냅니다. 방식은 `DELETE`, 주소는 같은 기록 주소이고 Body는 필요 없습니다. 이 요청은 기록과 사진을 실제로 지웁니다.

성공 응답의 `data.deleted`가 `true`인지 보고 목록을 다시 조회합니다. 해당 기록이 목록에서 사라졌다면 생성부터 삭제까지 한 흐름을 마친 것입니다. 컬렉션에 기록 ID 변수가 남아 있어도 그 기록이 다시 생기는 것은 아닙니다.

## 9. 선택 실습: 저장 전 초안 다시 만들기

재작성은 `draft` 상태에서만 가능합니다. 앞의 실습을 끝냈다면 새 테스트 기록으로 초안 생성 단계까지 다시 진행하세요. 이미 `saved`인 기록에 요청하면 `409 DRAFT_REQUIRED`가 나옵니다. 저장한 기록은 제목·본문을 직접 수정합니다.

`06` 초안 요청의 Body를 다음처럼 바꿔 보낼 수 있습니다.

```json
{
  "regenerate": true,
  "version": 5
}
```

`5` 역시 형식 예시이며 실제로는 최신 상세 응답의 `memory.version`을 넣습니다. 컬렉션 변수를 쓰려면 숫자 자리에 따옴표 없이 `{{memory_version}}`을 넣을 수도 있습니다. `regenerate`는 참거짓 값이어야 하고 버전이 오래되면 `409 VERSION_CONFLICT`로 거절합니다.

이 요청은 질문·답변을 유지하면서 제목·본문을 교체합니다. Postman이나 다른 편집창에서 고친 문장이 있다면 먼저 보관하세요. 성공 후 새 제목·본문을 읽고 최신 버전으로 저장합니다. 실습이 끝나면 해당 테스트 기록도 정리합니다.

## 10. 응답을 읽으며 오류가 난 단계 찾기

정상적인 앱 API 응답은 다음 형태입니다. 현재 구현에서는 생성과 삭제도 HTTP `200`을 돌려줍니다.

```json
{
  "ok": true,
  "data": { "memories": [] },
  "requestId": "요청마다 부여하는 확인 번호"
}
```

목록이면 `data.memories`, 기록 한 건이면 `data.memory`를 읽습니다. `requestId`는 요청 내용을 그대로 공유하지 않고도 오류를 구분하는 확인 번호입니다. 사진 조회는 JSON 대신 이미지 바이트를 반환하며 `/api/health`의 간단한 응답에는 공통 `requestId`가 없습니다.

실패 응답에서는 HTTP 상태와 `error.code`, `error.message`를 함께 봅니다.

```json
{
  "ok": false,
  "error": {
    "code": "INVALID_DATE",
    "message": "실제 날짜를 YYYY-MM-DD 형식으로 입력해주세요."
  },
  "requestId": "오류 확인 번호"
}
```

| 상태 | 이번 실습에서 확인할 것 | 예 |
|---|---|---|
| 400 | 날짜·답변·필수 조건 | 없는 날짜, 빈 답변 |
| 403 | 요청의 출처 설정 | 허용하지 않은 `Origin` |
| 404 | 기록 ID와 같은 호스트의 쿠키 | 없거나 다른 쿠키 소유인 기록 |
| 409 | 현재 단계·질문 ID·최신 버전 | 대화 후 업로드, 이미 답한 질문, 오래된 저장 |
| 413 | 요청 본문과 사진 합계 크기 | 업로드 전체 한도 초과 |
| 415 | Body 방식과 `Content-Type` | JSON 대신 일반 글 전송 |
| 429 | 짧은 시간에 반복한 변경 요청 | 앱 요청 수 제한 |
| 502·504 | 외부 AI의 인증·응답 형식·연결·대기 | 공급자 오류 또는 대기 초과 |
| 503 | 필수 설정값과 동시에 처리 중인 작업 수 | 설정 누락, 동시 처리 한도 |

Postman처럼 `Origin`이 없는 도구도 사용할 수 있지만 소유권 검사는 적용됩니다. 쿠키를 지우거나 호스트를 바꿨다면 이전 ID부터 다시 시도하기보다 해당 주소의 세션을 먼저 확인합니다. 대기 시간이 초과됐을 때는 처리가 이미 끝났을 수 있으므로 `09` 상세를 읽고 현재 상태를 확인한 뒤 재시도합니다.

## 11. 실습한 API를 다시 찾아보기

아래는 현재 앱의 전체 경로입니다. `{id}`와 `{photoId}`는 설명용 자리 표시이며 실제 요청에서는 응답으로 받은 UUID를 사용합니다. 여기의 앱 API는 CLOVA API와 다릅니다. Postman이 앱에 요청하면 앱 서버가 필요한 외부 서비스를 호출합니다.

| 방식 | 주소 | 역할 |
|---|---|---|
| GET | `/api/health` | 웹 서버의 간단한 응답 확인 |
| GET | `/api/app` | 모드·필수 설정 존재 여부·모델 구성 |
| GET | `/api/memories` | 내 기록 목록 |
| POST | `/api/memories` | 새 기록 생성 |
| GET | `/api/memories/{id}` | 내 기록 상세 |
| PATCH | `/api/memories/{id}` | 제목·본문 저장·수정 |
| DELETE | `/api/memories/{id}` | 기록과 사진 삭제 |
| POST | `/api/memories/{id}/photos` | `files` 사진 업로드 |
| GET | `/api/memories/{id}/photos/{photoId}` | 소유권 검사 후 사진 조회 |
| POST | `/api/memories/{id}/start` | 사진 관찰과 첫 질문 |
| POST | `/api/memories/{id}/answers` | 답변 반영과 다음 질문 |
| POST | `/api/memories/{id}/draft` | 초안 생성·명시적 재작성 |

입력별 정확한 한도와 공통 보안 규칙은 [API 계약서](API_CONTRACT.md)에서 다시 확인할 수 있습니다. 앱 실행과 NCP 설치를 이어 가려면 [README](../README.md)로 돌아갑니다.
