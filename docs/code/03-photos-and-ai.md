# 3. 사진 처리와 AI가 들어오는 구간 읽기

지금까지는 앱의 사용·통신·저장을 외부 AI 없이 확인했습니다. `ncloud`로 바꾸면 화면의 흐름은 같지만 사진 저장, 질문 생성, 글쓰기를 실제 NCP 서비스가 맡습니다. 앞 문서에서 따라온 요청·저장 경로를 기준으로 어떤 내용이 어디로 보내지는지 살펴보겠습니다. 이 문서는 구현을 설명하며 실제 계정의 모델 권한이나 운영 서버 적용을 확인했다는 뜻은 아닙니다.

## 3-1. 선택한 사진은 어떻게 전송되는가

[memory-api.js](../../src/lib/client/memory-api.js)의 `preparePhoto`를 먼저 엽니다. 브라우저는 원본 사진을 덮어쓰지 않고 전송용 사본을 만듭니다. 긴 변을 최대 1,600px로 줄이고 JPEG 품질 0.86으로 다시 인코딩합니다. 투명한 부분은 흰색이 됩니다. 이 재인코딩으로 원본 EXIF를 그대로 전송하지 않도록 했습니다.

브라우저와 서버는 서로 다른 위치에서 파일을 검사합니다. 앞에서 사용한 테스트 이미지를 Postman으로 직접 보낼 때는 브라우저 축소를 거치지 않는다는 점도 함께 기억하세요.

| 검사 위치 | 현재 기준 |
|---|---|
| 브라우저에서 선택 | JPG·PNG·WebP, 원본 각 30MiB 이하 |
| 브라우저에서 해독 | 8천만 화소 이하, 지나친 가로세로 비율 제한 |
| 브라우저에서 전송 준비 | 긴 변 1,600px, JPEG 품질 0.86 |
| 서버에서 받기 | 파일당 0보다 크고 5MiB 이하 |
| 서버에서 형식 검사 | 파일 시작 바이트와 선언한 형식 비교 |
| 기록에 추가 | 합계 3장까지, 대화 시작 전만 허용 |

서버는 헤더 바이트를 검사하지만 이미지 전체를 해독하거나 얼굴·글자를 가리지는 않습니다. 사진 속 주소·얼굴·차량번호·메시지는 재인코딩 뒤에도 남을 수 있습니다. EXIF를 줄이는 처리만으로 사진이 익명화되는 것은 아닙니다.

이후 저장·읽기 경로는 [photos.js](../../src/lib/server/app/photos.js)의 `putPhoto`·`getPhoto`·`signedPhoto`로 이어집니다. `ncloud` 사진은 비공개 Object Storage에 저장합니다. 브라우저가 읽을 때는 앱 사진 API가 쿠키와 소유자를 검사하고, CLOVA가 관찰할 때만 300초짜리 서명 URL을 전달합니다. 서명 URL은 그 시간 동안 읽기 권한을 가진 주소이므로 공개하지 않습니다.

중복 업로드는 정규화한 파일명과 SHA-256 내용 지문으로 비교합니다. 같은 이름·내용은 다시 추가하지 않지만 이름이 다르면 같은 내용도 별개 사진일 수 있습니다. 이 지문은 파일 비교용이며 사람을 식별하는 기능은 아닙니다.

## 3-2. 사진을 보고 질문한 뒤 사용자 말로 글쓰기

[ai.js](../../src/lib/server/app/ai.js)의 `observePhotos`·`nextQuestionTurn`·`makeDraft`를 차례로 엽니다. 사진 관찰에는 HCX-005, 질문·작성·검토에는 HCX-007을 사용합니다. 텍스트 작업은 `thinking.effort: high`로 요청합니다. 앱의 모델 선택은 코드에 있지만 해당 계정의 실제 이용 권한과 결과 품질은 별도로 확인해야 합니다.

```text
사진 1~3장 → HCX-005 관찰
  → 날짜·장소·이전 대화로 HCX-007 질문
  → 질문 형식·중복 검사, 필요 시 준비된 질문
  → 답변 전체로 HCX-007 작성
  → 원래 답변과 초안으로 HCX-007 검토
  → JSON·답변 ID·분량 검사
  → 사용자 확인·수정·저장
```

사진 관찰문은 질문을 만드는 참고 자료입니다. 일기 작성·검토에는 사진과 관찰문을 보내지 않고 날짜·장소·사용자 답변을 보냅니다. 사진에 보인 장면을 사용자가 경험한 사실로 그대로 채우지 않게 입력을 나눈 것입니다. 질문의 전제가 틀렸다면 사용자가 정정한 내용을 따르도록 지시합니다.

`nextQuestionTurn`은 새 질문을 `{"question":"짧은 한국어 질문 하나?"}` 형식으로 요청하고 [question-format.js](../../src/lib/server/app/question-format.js)의 `readQuestionText`로 결과를 검사합니다. 새로 생성하는 질문은 120자 이내의 한 문장이며 Q1 제목·마크다운·설계 설명을 넣지 않도록 했습니다. 서버가 여러 질문, 분석문, 너무 긴 응답, 출력 잘림을 발견하면 준비된 질문으로 대체할 수 있고 그 출처를 안내합니다.

기존 질문에서는 Q1·굵게 표시·질문 뒤 설계 설명처럼 확실히 해석할 수 있는 포장만 표시용 복사본에서 정리합니다. DB의 원문·질문 ID·답변은 유지합니다. 해석할 수 없는 옛 문장을 임의의 새 질문으로 바꾸지는 않습니다.

[question-plan.js](../../src/lib/server/app/question-plan.js)는 질문 관점을 상황·세부 장면·직전·직후·감각·사진을 남긴 이유 등으로 나눕니다. 문자열 유사도와 알려진 의도를 검사해 반복이면 쓰지 않은 관점의 준비된 질문을 고릅니다. 이 한국어 규칙만으로 모든 의미 중복을 완벽히 판단할 수는 없습니다.

## 3-3. 초안이 짧아지거나 AI 응답이 잘못됐을 때

글쓰기는 첫 요청에서 작성하고 두 번째 요청에서 원래 답변과 비교해 검토합니다. 첫 JSON이 정상이어도 검토를 거칩니다. 첫 결과의 형식을 읽을 수 없다면 두 번째 요청에는 초안을 `null`로 보내 원래 답변에서 다시 작성하게 합니다. 행동·이유·대화·감정과 나중에 정정한 사실을 보존하도록 지시하고 문단마다 근거 답변의 `answerIds`를 받습니다.

[draft-format.js](../../src/lib/server/app/draft-format.js)의 `assembleDraft`가 답변 ID를 확인합니다. 모든 ID가 정확히 한 번 포함돼야 하며 알 수 없는 ID·누락·중복을 거절합니다. 공백을 정리한 답변 길이의 합이 160자 이상인데 초안 본문이 그 55%보다 짧으면 거절합니다. 본문 상한도 32,000자로 검사합니다. 그러나 ID와 길이가 맞는다는 것만으로 실제 의미까지 모두 보존됐다고 증명할 수는 없습니다. 메인 README에서 해 본 원문 대조가 실제 AI 사용 때도 필요합니다.

형식·분량 검사를 끝내 통과하지 못하면 답변 원문으로 초안을 만들고 화면에 AI 글을 완성하지 못했다고 알립니다. 인증·네트워크 오류는 실패로 안내합니다. `ncloud` 설정이 잘못됐다고 몰래 demo로 바꿔 성공한 것처럼 보여 주지는 않습니다.

## 3-4. 기다리는 시간과 사용량 이해하기

모델·토큰 상한은 [clova-models.js](../../src/lib/server/clova-models.js)에서, 실제 HTTP 호출은 [day1/clova.js](../../src/lib/server/day1/clova.js)에서 확인합니다. 사진·질문·글쓰기는 서로 다른 요청입니다. 작성과 검토를 나누면 호출 수, 대기 시간, 비용이 늘 수 있습니다. 현재 코드에 정한 상한은 다음과 같습니다.

| 작업 | 코드의 설정 |
|---|---|
| 사진 관찰 | 최대 1,024 출력 토큰 |
| 질문 | 최대 20,480 completion 토큰 |
| 작성·검토 각각 | 최대 32,768 completion 토큰 |
| 텍스트 요청 한 번 | 90초 대기 |
| 브라우저 기본·초안 요청 | 210초 대기 |
| Nginx 응답 | 240초 대기 |

토큰은 글자 수와 다르며 추론 모델에서는 추론 사용량도 상한에 영향을 줍니다. 이 숫자는 최대값이므로 매번 그만큼 출력하거나 사용하는 것은 아닙니다. 대기 시간이 길어졌다면 앞 문서에서 본 것처럼 재조회로 반영 여부를 먼저 확인합니다.

이제 브라우저 입력부터 서버 검사·저장, 사진·AI 처리, 응답을 받아 화면을 바꾸는 과정까지 연결했습니다. 클라우드에 설치하려면 [메인 README](../../README.md)의 NCP 준비·설치 순서로 돌아가세요. 먼저 코드를 조금 바꿔 보고 싶다면 [수정 연습과 파일 안내](../CODE_MAP.md)에서 안내 문구 하나를 고치고 검사하는 실습으로 이어 갑니다.
