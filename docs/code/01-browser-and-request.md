# 1. 브라우저 입력에서 요청 본문까지

화면에서 답변이 사라지고 다음 질문이 뜨는 사이에 브라우저와 서버가 통신했습니다. 이번에는 통신 한 건을 눈으로 확인하고 그 요청을 만드는 화면 코드를 읽습니다. [시작 안내](README.md)에서 준비한 테스트 기록으로 진행합니다.

## 1-1. 브라우저와 서버가 하는 일 구분하기

지금 브라우저는 화면을 그리고 입력을 받습니다. PowerShell에서 켠 Next.js 서버는 요청을 받아 검사하고 기록을 저장합니다. 둘 다 내 PC에서 실행되지만 맡은 일은 다릅니다. 요청하는 쪽을 클라이언트, 받아 처리하는 쪽을 서버라고 부릅니다.

이 프로젝트는 화면과 서버 코드를 하나의 Next.js 프로젝트에 담았습니다. 사용자가 보는 화면을 프론트엔드, 서버의 처리·저장을 백엔드라고 부르기도 합니다. 같은 저장소 안에 있어도 비밀 키를 사용하는 코드는 서버에서만 실행합니다.

```text
브라우저: 답변 입력 → 요청 보내기
                         ↓
Next.js 서버: 소유자·입력 검사 → 답변 반영 → 다음 질문 → 저장
                         ↓
브라우저: 응답 받기 → 다음 질문 표시
```

이 경로를 API라고 부르는 약속으로 연결합니다. API에는 어떤 주소에 어떤 방식으로 무엇을 보내고, 어떤 결과를 받을지가 정해져 있습니다. 우리 앱 API는 브라우저와 앱 서버 사이의 약속이며 뒤에서 연결할 CLOVA API와는 다릅니다.

## 1-2. 답변 요청 한 건 찾기

앱 브라우저에서 새 테스트 기록을 만들고 첫 질문 화면까지 갑니다. Chromium 계열 브라우저라면 `F12`로 개발자 도구를 열고 **Network** 탭을 선택합니다. 브라우저에 따라 메뉴 이름이나 단축키가 조금 다를 수 있습니다.

개발자 도구를 연 상태에서 답변을 입력하고 **답변 보내기**를 누릅니다. Network의 요청 목록에서 `answers`로 끝나는 항목을 찾습니다. 목록이 많다면 `answers`를 검색하거나 Fetch/XHR 필터를 사용합니다.

그 요청의 Headers에서 다음 두 항목을 확인합니다.

```text
Request URL: http://127.0.0.1:3000/api/memories/기록ID/answers
Request Method: POST
```

실제 주소에는 서버가 만든 기록 ID가 들어갑니다. URL의 끝부분인 `/api/memories/.../answers`는 '이 기록에 답변을 제출한다'는 경로입니다. `POST`는 서버에 작업을 요청하는 방식입니다. 목록 읽기는 `GET`, 제목·본문 변경은 `PATCH`, 삭제는 `DELETE`를 사용합니다.

## 1-3. 입력한 문장을 요청 본문에서 찾기

이제 같은 요청의 Payload를 엽니다. 브라우저가 서버에 보낸 본문이 아래와 비슷하게 보입니다.

```json
{
  "questionId": "서버에서 받은 현재 질문 ID",
  "answer": "발표가 끝나서 친구와 쉬고 있었어요.",
  "skipped": false
}
```

입력 문장은 `answer`에 담깁니다. `questionId`는 어느 질문에 대한 답인지 알려 주는 값이고 주소의 기록 ID와는 다릅니다. `skipped`가 `false`이면 실제 답변이며 `true`이면 건너뛰기입니다. `false`라는 참거짓 값과 `"false"`라는 문자열은 다른 값입니다.

이 모양을 JSON이라고 합니다. 이름과 값을 짝으로 전달하는 텍스트 형식이며 필드 이름·문자열에는 큰따옴표를 씁니다. 서버는 약속한 필드와 값의 종류가 맞는지 검사합니다. 입력창에 보이는 글이 이 본문으로 바뀌어 전송된다는 점을 확인하면 됩니다.

## 1-4. 응답에서 같은 답변 찾기

같은 요청의 Response를 엽니다. 성공했다면 `ok: true`와 `data.memory`가 있고, 그 기록의 `turns` 안에서 방금 보낸 답변을 찾을 수 있습니다. `turns`는 지금까지의 질문·답변을 순서대로 담는 목록입니다. 다음 질문이 생성됐다면 그 항목도 함께 들어옵니다.

답변 요청의 응답은 다음처럼 읽습니다. 아래는 `turns`의 답변 하나와 응답 틀만 남긴 예시이며 실제 응답에는 기록 ID·날짜·다음 질문 등도 있습니다.

```json
{
  "ok": true,
  "data": {
    "memory": {
      "turns": [
        {
          "question": "이 사진을 찍던 순간에는 무엇을 하고 있었나요?",
          "answer": "발표가 끝나서 친구와 쉬고 있었어요.",
          "skipped": false
        }
      ]
    }
  },
  "requestId": "요청마다 부여하는 확인 번호"
}
```

목록 요청은 `data.memories`, 답변 요청은 `data.memory`처럼 기능에 따라 결과 필드가 다릅니다. `requestId`는 오류가 났을 때 어느 요청인지 구분하는 번호입니다. 사진 조회는 JSON 대신 사진 파일을 보내고, `/api/health` 응답에는 이 공통 번호가 없습니다.

HTTP 상태 200은 요청이 정상 처리됐다는 표시입니다. 이 앱은 생성·삭제도 성공 상태로 200을 사용합니다. 오류 상태와 `ok: false`가 오면 응답의 `error.code`, `error.message`를 읽습니다. 오류가 표시됐다고 브라우저가 서버에 전혀 도달하지 못한 것은 아닙니다. 서버가 요청을 받은 뒤 조건을 검사하고 거절했을 수도 있습니다.

Payload의 문장과 Response의 답변이 연결되는 것을 확인했다면, 이제 그 요청을 만드는 함수를 찾아보겠습니다. 편집기로 프로젝트 폴더를 열고 아래 파일과 함수 이름을 검색합니다. 코드 블록은 읽는 예시이며 PowerShell 명령이 아닙니다.

## 1-5. 화면 파일에서 답변을 보내는 함수 찾기

[MemoryApp.js](../../src/components/MemoryApp.js)를 열어 `submitAnswer`를 검색합니다. 함수는 여러 줄의 작업에 이름을 붙인 것입니다. `submitAnswer`는 현재 질문과 입력값을 확인한 뒤 서버에 답변을 보내는 일을 맡습니다.

파일에는 다음과 같은 호출이 있습니다.

```javascript
const data = await memoryApi.answer(
  active.id,
  current.id,
  answer.trim(),
  skipped,
);
updateMemory(data.memory);
setAnswer("");
```

`active`는 현재 기록, `current`는 현재 질문입니다. `active.id`는 기록 안의 `id` 값을 읽습니다. `answer.trim()`은 입력 문장 앞뒤의 공백을 정리합니다. 괄호 안에 나열한 네 값은 함수를 실행할 때 넘기는 재료이며 이를 인자라고 부릅니다.

`const data`는 받은 결과를 `data`라는 이름으로 쓰겠다는 뜻입니다. `const`로 선언한 이름에는 다른 값을 다시 대입하지 않습니다. 값에는 문장 같은 문자열, `3` 같은 숫자, `false` 같은 참거짓 값이 있습니다. 이 함수는 그중 현재 답변 문자열과 건너뛰기 여부를 서버에 보냅니다.

`async` 함수 안에서 쓰는 `await`는 요청 결과를 기다린 뒤 다음 줄로 진행하게 합니다. 네트워크 요청은 바로 끝나지 않기 때문에 응답을 받기 전에 다음 질문을 확정해서 보여 줄 수는 없습니다. 성공해야 `data.memory`로 화면을 바꾸고 입력창을 비웁니다. 실패하면 오류 안내를 보여 주고 보낼 답변은 유지합니다.

## 1-6. 통신 파일에서 요청을 만드는 부분 찾기

이제 [memory-api.js](../../src/lib/client/memory-api.js)에서 `answer:`를 찾습니다. 방금 본 네 인자를 서버가 읽는 필드에 넣습니다.

```javascript
answer: (id, questionId, answer, skipped = false) =>
  request(`${memoryPath(id)}/answers`, {
    method: "POST",
    body: { questionId, answer, skipped },
  }),
```

`body: { questionId, answer, skipped }`의 중괄호는 관련 값을 하나로 묶은 객체를 만듭니다. 예를 들어 기록 한 개도 다음처럼 여러 필드를 묶은 객체로 읽을 수 있습니다.

```javascript
const memory = {
  date: "2026-10-29",
  place: "동네 카페",
  questionLimit: 3,
  photos: [],
};
```

`memory.place`는 장소를 읽고 `photos: []`는 아직 사진 항목이 없는 배열을 뜻합니다. 객체는 필드 이름으로 값을 찾고 배열은 여러 항목을 순서대로 담습니다. 기록의 사진 목록은 `photos`, 대화 목록은 `turns` 배열입니다.

같은 파일의 `request` 함수까지 올라가면 브라우저의 `fetch`로 HTTP 요청을 보내는 부분이 보입니다. 일반 객체인 본문은 `JSON.stringify`로 JSON 텍스트가 되고 사진 파일은 `FormData`로 전송됩니다. 그래서 Network에서 답변 요청은 JSON으로, 사진 요청은 다른 형태로 보였습니다.

`credentials: "same-origin"`은 같은 사이트 요청에 쿠키를 보내게 하는 설정입니다. 이 파일에 DB 비밀번호나 CLOVA 키를 넣지 않습니다. 브라우저에 전달되는 코드이기 때문입니다.

## 1-7. 서버 응답을 기다리는 동안과 받은 뒤의 화면

다시 [MemoryApp.js](../../src/components/MemoryApp.js)의 `updateMemory(data.memory)`로 돌아옵니다. 서버가 확정해 돌려준 기록으로 현재 화면 상태를 바꾸는 부분입니다. React는 그 상태를 기준으로 현재 질문, 이전 답변, 다음 버튼을 다시 그립니다.

입력창도 React 상태로 관리합니다. 다음 문장은 현재 입력값과 값을 바꾸는 함수를 함께 만듭니다.

```javascript
const [answer, setAnswer] = useState("");
```

`answer`는 현재 입력한 문장이고 `setAnswer`는 그 값을 바꿉니다. 타이핑만 하면 브라우저 상태가 바뀝니다. 서버 기록은 답변 요청이 성공해야 바뀌므로 화면에 글이 보인다는 것과 저장됐다는 것은 구분해야 합니다. 메인 README에서 저장 후 다시 열어 본 이유가 여기에 있습니다.

이제 브라우저에서 어떤 값을 보내고 받은 결과로 어떻게 화면을 바꾸는지 읽었습니다. 다음 문서에서는 아직 살펴보지 않은 서버 검사와 저장을 연결합니다. 처음에는 각 함수의 모든 줄보다 '받는 값과 다음에 부르는 함수'를 찾아보세요. 코드의 한국어 주석도 함수 목적·입력·결과·실패 조건을 읽는 데 도움을 주지만 실제 규칙은 코드와 검사 결과를 함께 확인합니다.

요청을 만드는 코드는 확인했지만 이 파일만으로 다른 사람의 기록에 답할 수 있는지나 중복 저장 여부까지 정하지는 않습니다. 그 판단은 서버에서 다시 합니다. 방금 Network에서 본 `answers` 주소를 다음 문서의 서버 입구와 비교해 보세요.
